| 2026-09-05 | `POST /units/{unit_code}/link` answers 404 on an `unlisted` unit (as the public endpoint does) and 409 `unit_unavailable` on a `maintenance` one. Spec names only the occupied case. | An unlisted sticker must read as an unknown code; maintenance is a real, temporary refusal worth distinguishing. |
| 2026-09-05 | `start_date` accepts `today−7 … today+365`; `PUT /me/profile` requires next of kin. | Spec fixes only the −7 backstop; the ceiling stops a request reserving a unit indefinitely, and next of kin is required to reach `kyc_status: submitted`, which gates linking. |
| 2026-09-05 | Approving a link request leaves the unit `vacant`; `onLinkApproved(ctx, q, req)` in `link_handlers.go` is the (no-op) seam where Phase 4 creates the contract. | A unit becomes occupied when a contract activates, so an approved-then-abandoned request cannot strand it. |
| 2026-09-05 | `notification_log` gains `to_phone`, `body`, `error`, `attempts`; the Phase 3 worker makes one attempt with no backoff. | The worker sends from a single row read; the 3-attempt retry pool is Phase 6 scope (SPEC §6). |
| 2026-09-05 | `unit_link_requests.reason` (000002) replaced by `rejection_reason` in 000004. | Two columns for the same fact leave two places to look. |
| 2026-09-05 | Auto-approved link requests have `decided_by_user_id` NULL (system decision). `end_date` is exclusive: `end_date = start_date + term_days` (SPEC §4) — the day after the last schedule row's inclusive `period_end`. | Spec silent on the auto-approve actor; the end-date convention is SPEC §4's, and the enduser preview was realigned to it. |
| 2026-09-05 | Link approval creates the contract in the same transaction (manual + auto-approve) from the org default template; approving an already-approved request with no contract backfills one. Approval fails whole if the contract cannot be written (unpriced unit, no template). | FLOWS 3.3; a renter must never be told "approved" with nothing to sign. |
| 2026-09-05 | Landlord countersign on the FLOWS 3.6 path records `contract_signatures.method = landlord_recorded` with a required reason; normal activation records `otp_accept` via session. Contract reads (`{id}`, `/document`, `/verify`, `/schedules`) accept renter or org audience; writes stay one-sided. | Spec silent on method value for the no-phone case; audit needs the distinction. |
| 2026-09-05 | Termination waives schedules whose `period_start` is after `effective_date`; the period in progress stands. `due_day` falls back to `orgs.settings.due_day`. | Simplest rule consistent with FLOWS 6.5. |
| 2026-09-05 | An overpayment lands on the schedules *after* the target, in due order, skipping settled and waived rows; one on the last unpaid schedule answers 409 `exceeds_contract_balance` (not `overpay_confirm_required` — there is nothing to prompt about). | API.md fixes the rollover but not the edge; a confirm prompt with no destination is not a prompt. |
| 2026-09-05 | Recording a payment sets only `paid`/`partial` (API.md); the overdue re-flag is left to the sweep, which every schedule read runs org-scoped first, so no client can observe the gap. | API.md's record and reverse rules disagree on `overdue`; this keeps both literal without a stale read. |
| 2026-09-05 | `payments.status` keeps its 000002 `confirmed` value in the CHECK constraint even though Phase 5 only ever writes `recorded`/`reversed`. | `confirmed` is the reserved gateway seam (SPEC §5.7); narrowing it now would have to be widened again. |
| 2026-09-05 | The on-demand overdue sweep run by `GET /schedules` and `GET /me/schedules` is not audited; only `POST /admin/jobs/overdue` writes `payment.overdue_run`. | A read's own housekeeping would otherwise write an audit row per page view and bury the trail. |
| 2026-09-05 | `GET /me/schedules` shows the bank account of the org behind `next_due` only (a renter may rent from several orgs); with nothing outstanding, `bank_account` is `null`. | API.md gives one `bank_account` field for a possibly multi-org list; the account that matters is the one for the next payment. |
| 2026-09-05 | `POST /payments` on a fully settled contract, and one naming a schedule of another contract, answer 409 `exceeds_contract_balance` and 404 respectively. | Spec silent; both follow the existing "id not in your scope is a 404" and "money the contract cannot take is refused" rules. |
| 2026-09-05 | `GET /schedules` pages by `(due_date, id)` ascending rather than the `(created_at, id)` descending cursor the other listings use. | The board is read forward — the next thing owed is the first thing shown. Same cursor encoding, so clients treat it identically. |
| 2026-09-05 | `orgs.settings.notifications` holds sender name, send hour, per-kind toggles and template overrides; `language` in the notification-settings endpoint reads and writes the existing `orgs.settings.sms_language` rather than storing a second copy. | Two places to set one language is two places for it to be wrong; API.md names the field `language`, and PATCH `/org` already names it `sms_language`. |
| 2026-09-05 | The org template whitelist is exactly API.md's eight variables. The platform defaults additionally use `{{reason}}`, `{{start_date}}` and `{{next_amount}}`; an org override of those kinds simply does without them. An override of `thank_you` replaces both the "next payment" and the "all paid" wordings. | The whitelist is a locked contract; widening it silently would be a deviation, and the extra three belong to one kind each. |
| 2026-09-05 | `notification_log.status` gains `sending`, the state between the worker's atomic claim and the provider's answer. The startup sweep returns rows left `sending` for over five minutes to `queued`. | The claim (`… WHERE status='queued' RETURNING`) needs a status to move to; without the sweep a crashed worker would strand the message. |
| 2026-09-05 | With `MaxAttempts` at API.md's three, the 1s/5s/25s backoff schedule uses 1s and 5s (the pauses between attempts); the 25s rung is kept in the table as the next step. Delays are injectable so tests do not spend six seconds per failure. | Three attempts have two gaps between them; the schedule is written down whole rather than truncated. |
| 2026-09-05 | `POST /notifications/custom` with `selected` counts an unrelated renter id as `skipped`, never a 404. A renter with no phone on file is also `skipped`. | A broadcast must not become a way to probe another org's directory, and one missing number must not fail a batch of forty. |
| 2026-09-05 | The scheduler walks orgs one at a time with org-scoped queries rather than one cross-org sweep, so the isolation guard applies to it unchanged. `RunOnce` takes no Redis: the caller enqueues the ids it returns. | Keeps the sweep testable against a bare database, and keeps Redis carrying the work item rather than the truth (SPEC §2.2). |
| 2026-09-05 | The sender ID is resolved inside the worker's claim (`orgs.settings->notifications->sender_name`) rather than stored on the notification row. Auth OTPs send with the platform default (no org is known yet); the contract-signing OTP uses the landlord's. | One round trip on the send path, and a sender-name change applies to messages already queued. |
| 2026-09-05 | `GET /admin/jobs` reports each job's last run from the newest `audit_log` row for its action (`contract.lifecycle_run`, `payment.overdue_run`, `notification.scheduler_run`) rather than from a new `job_runs` table. Migration 000009 adds only `orgs.suspended_at` / `orgs.suspended_reason` and an `(action, at DESC)` index. | The jobs already audit themselves; a second store could only disagree with the first. |
| 2026-09-05 | Suspension is enforced in `RequireOrg` (and the org half of `RequireContractParty`) as 403 `org_suspended`, decided by a Redis flag `org:suspended:{id}` written on suspend/activate with a cached `SELECT status FROM orgs` fallback. Renters and platform admins are unaffected, and login itself still succeeds. | Redis is ephemeral (SPEC §2.2), so a missing flag must cost a query, never open a suspended org. A renter is not suspended because their landlord is, and an operator needs "wrong password" to stay distinguishable from "org closed". |
| 2026-09-05 | A suspended org's queued SMS is left `queued` — `ClaimNotification` gains `AND o.status = 'active'`, so the claim finds nothing and the worker returns as it does for an already-taken row. Nothing is marked `failed`. | Reactivation should release the backlog, not leave a trail of errors the landlord has to retry one by one. |
| 2026-09-05 | Report periods and collections buckets are read on the Dar es Salaam wall clock (the zone SPEC §6 already uses for send hours); occupancy is `occupied / (occupied + vacant)`, excluding `unlisted` and `maintenance`; `days_vacant` counts from the last ended/terminated contract's `end_date`, else the unit's creation. | API.md fixes the shapes, not the boundaries. A month must be the month it is where the landlord stands, and a room taken off the market is not a vacancy they are failing to fill. |
| 2026-09-05 | `POST /admin/orgs/{id}/suspend` requires a non-empty `reason` (stored on the org and in the audit `after`); activate clears it. `dashboard_prefs` refuses unknown keys as well as unknown card ids. | Suspending a tenant without saying why is the one admin action nobody can reconstruct afterwards; silently dropping a setting a landlord thought they saved is worse than a 400. |
| 2026-09-05 | Exactly **one** recommended payment period per org, enforced by a partial unique index (`payment_periods (org_id) WHERE is_recommended AND deleted_at IS NULL`); bootstrap and seed badge Monthly, `POST /org/payment-periods/{id}/recommend` moves it, and the other three seeded presets stay restorable but unbadged. | A badge on all four presets told the renter nothing, so "recommended first" was not an ordering at all (client request #8, confirmed 5 Sep). |
| 2026-09-05 | `{{rent}}` in a contract template is the amount **per payment period** (`round(rent_amount × payment_period_days / rent_period_days)`, the schedule's own rounding); the unit's price basis moves to a new `{{rent_basis}}` variable, and `GET /contracts/{id}` carries `rent_per_period`. Existing signed contracts are untouched (snapshot rule) and `snapshot_hash` is unaffected — the hash covers already-rendered terms. | The test contract read "TZS 100,000 per Quarterly (90 days)" for a 100,000-per-30-days room: the signed document stated the wrong figure. Only new contracts can change; a re-issue is the fix for an existing one. |
| 2026-09-05 | Language is stored per user (`users.locale`, `sw|en`, default `sw`), chosen at registration/signup; `orgs.settings.sms_language` survives only as the fallback for renters with no preference, and public pre-login pages default to the org language with a visible SW/EN toggle whose choice is carried into registration. | One renter's language is a fact about the renter, not about their landlord; the toggle gives a first-time scanner a way in before any account exists. |
| 2026-09-05 | SMS credits are prepaid per org with **no expiry and no monthly reset**, debited at send time at **1 credit per 160-character GSM segment** (70 for UCS-2), with `otp`/security kinds exempt; an empty balance parks the row as `held_no_credit` (never `failed`) and a top-up releases held rows in queue order. | PLAN2 open question 1's defaults, confirmed with the client. Charging per segment matches what Beem bills; `failed` would invite retries that cannot succeed. |
| 2026-09-05 | Platform message templates move from Go constants into `platform_templates` (seeded by migration, so the table is authoritative from day one; the constants remain the last-resort fallback), with a per-kind `locked` flag — `otp` locked out of the box — and an org override of a locked kind refused with 409 `template_locked`. | The admin needs to edit wording without a deploy (#12), and the OTP message is security copy no landlord should be able to rewrite. |
| 2026-09-05 | One org theme applies to **both** the landlord and the renter apps; the admin app is never themed. | PLAN2 open question 4's default: a renter and their landlord are looking at the same business, and platform staff must always see the platform's own chrome. |
| 2026-09-05 | Expense receipts live in a new MinIO bucket `receipts`, key `{org_id}/{expense_id}.{ext}`, ≤ 5 MiB, `image/jpeg`/`image/png`/`application/pdf`. | PLAN2 open question 5's default (PDF allowed); a separate bucket keeps the presigned-path prefix rule of the other buckets and lets the receipt policy differ from KYC's. |
| 2026-09-05 | `make build` sets `NEXT_DIST_DIR=.next-build` for every workspace (plain `next build` was overwriting the running dev servers' `.next`); new `make apps-restart` restarts only the three Next.js dev servers (proxy, ngrok, api untouched) | Phase 9 build clobbered the preview; recovery needed a scoped restart target |
| 2026-09-05 | Rent shown "as displayed": `rent_per_period` is derived (not hashed); existing contracts keep their snapshot wording; only new contracts render `{{rent}}` per payment period | Snapshot rule (SPEC §5.5) |
| 2026-09-05 | Stamp inks are not org-themable but get a fixed dark step (`#4ec07f` paid / `#ff8a80` overdue) under `data-theme="dark"`, same as the chart palette | Fixed stamps measured 2.8–3.4:1 on dark paper |
| 2026-09-05 | Theme presets: backend `presets.json` is the source of truth; `packages/ui` keeps a generated offline copy guarded by `TestPresetsMatchUICopy` | Frontends need a fallback before the API answers; drift must fail the build |
| 2026-09-05 | `night_ledger` primary is `#96b4ff` (not `#7c9cff`) so `on_primary/primary` passes 4.5:1; colours canonicalised lower-case; `source:"legacy"` only when `primary_color` differs from the schema default | Every preset must pass the validator |
| 2026-09-06 | Invalid `locale` → 400 (codebase-wide validation convention), not 422; bulk send keeps scalar `queued` and adds `by_language:{sw,en}` | Keep Phase 6 shapes stable |
| 2026-09-06 | i18n: apps own flat `en.ts`/`sw.ts` dictionaries; `make lint` runs `i18n-check` (key parity + placeholder parity); server-provided data (period labels, unit names, template HTML) is never translated client-side | Data vs chrome |
| 2026-09-06 | OTP became a platform template kind `otp` (`{{code}}`) rendered in the recipient's locale; excluded from landlord-editable kinds | Locale-aware security text |
| 2026-09-06 | SMS credits: debit happens at the send attempt inside the worker's claim transaction (a provider failure still consumes the credit); top-up releases **all** held rows oldest-first and the surplus is simply held again | One place counts segments |
| 2026-09-06 | `otp` is not org-overridable at all, so it never appears in a landlord's `locked_kinds`/`platform_templates`; the admin UI shows it locked | Locked-by-default kind is invisible to landlords rather than read-only |
| 2026-09-06 | Platform template body cap 480 chars (org override cap stays 320); `SMS_CREDIT_EXEMPT_KINDS` env (default `otp`, `none` = charge everything) | Ops knob for exemptions |
| 2026-09-19 | `GET /proofs` pages **oldest first** (`created_at` ascending), unlike every other org listing. | A queue of claims is worked forward: the renter who has waited longest is the one to answer next, the same reasoning as `GET /schedules` ordering by `due_date`. |
| 2026-09-19 | `POST /proofs/{id}/accept` runs the existing `POST /payments` allocator rather than writing a payment of its own, and lets its **409s** (`overpay_confirm_required`, `exceeds_contract_balance`) propagate unchanged. | One allocator means a proof and a manually recorded payment can never split a schedule differently; propagating the 409 lets the landlord app reuse the confirm sheet it already has. |
| 2026-09-19 | **No SMS on proof submit** — only `proof_rejected` (and the existing `thank_you` on accept) is sent. The in-app badge and the `proofs` dashboard card are the landlord's signal. | The same rule as signing: the landlord lives in the dashboard, and a text per upload would spend credits on something they are already looking at. A rejection is the only outcome the renter cannot see coming. |
| 2026-09-19 | An accepted proof whose payment is later reversed stays **`accepted`**; the payment carries the reversal. | A proof is a claim that was answered — rewriting the answer afterwards would lose the fact that it was accepted on the day it was. |
| 2026-09-19 | `POST /imports/{batch_id}/commit` is **all-or-nothing in one transaction**; rows with errors are refused unless `skip_errors=true`, which drops them and commits the rest. Import writes call the same service functions as the manual endpoints, never raw SQL. | A landlord must never end up with half a spreadsheet and no way to tell which half; sharing the service functions means one set of validation rules rather than a second, looser one for files. |
| 2026-09-19 | The `renters` import **never activates a contract** — it stops at `pending_signature` and the `contract_ready` SMS is held until commit. | Activation needs a signature row (SPEC §5.5); a spreadsheet is not consent. The landlord still has the FLOWS 3.6 countersign path for a renter who cannot sign. |
| 2026-09-19 | The `payments` import resolves contracts in `active|expiring|**ended|terminated**`, unlike `POST /payments`. | The point of the import is history, and history usually belongs to a tenancy that has finished. A row over the contract balance is still an error, raised in the preview. |
| 2026-09-19 | Undo window for a committed batch is **24 h**; after that the batch is a normal part of the ledger. | Long enough to notice a wrong file the next morning, short enough that "removed when untouched since" is still a safe test — a month later the imported rows have schedules, payments and edits hanging off them. |
| 2026-09-19 | MinIO images pinned to cached release tags (`minio/minio:RELEASE.2025-04-22T22-12-26Z`, `minio/mc:RELEASE.2025-04-16T18-13-26Z`) in `docker-compose.yml` instead of `latest`. | `minio/minio:latest` is no longer published, so `make up` failed on a cold pull; the pinned tags are the newest ones already in the local image cache. |
| 2026-09-20 | The `payments` import writes through its own `applyImportedPayment` (same allocator math, same `payment_allocations` rows) instead of `allocatePayment`, because the handler path refuses `ended|terminated` contracts that history legitimately lands on. A parity test pins both paths to identical schedule and allocation outcomes. | SPEC §6 wants one write path; the reviewer flagged the split, and the test is the guard until the allocator grows a "historical" mode. |
| 2026-09-20 | Phase 16 dashboard cards (`upcoming`, `proofs`) are in the default order for orgs without saved prefs; an org that already customised keeps its list and adds them from Customize. | Saved prefs are the landlord's choice; silently re-adding cards would undo it. |
| 2026-09-20 | Assisted onboarding writes the code into the **same Redis slot** as the SMS path (`otp:{purpose}:{phone}`, or the contract sign slot) instead of a parallel verifier. | `POST /auth/otp/verify`, `/auth/register/renter` and `/contracts/{id}/sign` stay untouched; one verifier means one set of attempt limits and one audit trail. An assisted issue deliberately replaces an SMS code still in flight. |
| 2026-09-20 | Assisted issues bypass the per-phone send limiter and 60 s cooldown and are limited **per org** (30/h) and per session (10). | The landlord vouches for the number in person; the abuse case is a leaked landlord account, so the budget belongs to the org. Verify attempts (5/phone) are unchanged. |
| 2026-09-20 | The renter never has an assisted code entered *for* them: the landlord shows it, the renter types it on their own device, and a witnessed signature is an ordinary `otp_accept` row plus `witnessed_by_user_id`. The no-phone case stays `landlord_recorded`. | Keeps the signature the renter's own act (SPEC §5.5); the witness stamp is an audit fact, not a new signature method. |
| 2026-09-20 | Assist sessions live in Postgres (`assist_sessions`), the code only in Redis; each issue writes `notification_log` `channel=in_person, status=shown` with an empty body. | The landlord screen polls status and the admin sees volume beside SMS, but a code must never be persisted (same rule as production logs). |
| 2026-09-20 | `GET /public/assist/{id}` returns only `unit_code`, `purpose`, `status`. The renter types their own phone. | A session id in a QR is shareable; the phone is not put in a URL or an unauthenticated response. |
| 2026-09-20 | A session past `expires_at` reads as `closed` everywhere (status, `status_detail`, the 409 on refresh) although the stored column is still `open`; every lookup filters on `expires_at > now()`. | No sweep job to run and nothing to go stale: expiry and closure are the same event from the landlord's screen, and the `(org_id, phone) WHERE status='open'` unique index is released the moment the window lapses. |
| 2026-09-20 | `GET /assist` returns each session in the full `GET /assist/{id}` shape rather than a bare session object. | The list screen shows the same status line as the detail screen and polls every 5 s; one fetch instead of one per row. |
| 2026-09-20 | `notification_log` gained a paired CHECK (`channel = 'sms' OR status = 'shown'`) alongside the widened channel and status lists. | Widening two independent CHECKs would also admit a `shown` SMS row — a message that claims to have been sent and shown at once. The pairing is stated once in the schema rather than trusted to every writer. |
| 2026-09-20 | Phases 18.2/19/20 run as four concurrent Opus lanes in the **single working tree on one branch** (`phase-19-20`), path-disjoint, each committing only its own paths, instead of a branch per lane. | One checkout has one HEAD, and every lane needs the live preview (:3001–3003 hot reload, `make api-restart`) to verify, which a git worktree would cut off. Lanes still commit as they go, so a lane killed mid-flight loses nothing — the only thing given up is the per-lane merge boundary. |
| 2026-09-20 | A NIDA reveal is its **own POST endpoint**, not a `?reveal=1` flag on the existing renter/user reads. | A flag on a GET would be cacheable, prefetchable and easy to add to a URL by accident, and the audit row would hang off a read. A separate POST makes the audit row unmissable and the number un-cacheable. |
| 2026-09-20 | Phase 19 adds **no new access path to KYC documents** — only the NIDA number is revealable; `kyc.view` (already audited, presigned, short-lived) stays exactly as it is. | The complaint from the field is that the number is write-only, not that the document is hard to reach. Widening document access would be a separate decision with a separate deterrent story. |
| 2026-09-20 | A NIDA reveal is a **POST** (`/renters/{user_id}/nida/reveal`), never a query flag on the renter card, and its 200 carries `Cache-Control: no-store`. The audit row records the actor, the actor kind and the optional reason — never the number. | A GET can be cached, prefetched, logged by a proxy and pasted into a chat; a flag on an existing read would make the audit row easy to forget when a new caller is added. Auditing the *act* rather than the data keeps the trail readable by more people than may see the number. |
| 2026-09-20 | The reveal limiter is **60/h per org**, not per member of staff (the platform reveal is 60/h per admin). | The abuse case is a leaked landlord account walking the directory; an owner and a manager scraping in turn must not get two budgets. |
| 2026-09-20 | The renter's `nida_reveals` list on `GET /me/profile` shows who looked and when, but **not the reason** the actor typed. | The reason is the org's note to itself, often about a police report or a guarantor; the deterrent is that the renter can see the reveal happened, which does not require showing them what was written about them. |
| 2026-09-20 | A landlord may correct a renter's name only while the renter has signed **no** contract with **any** org (409 `renter_signed`); after that it is theirs to fix from their Profile. The signature check is deliberately cross-org. | A signature anywhere makes the name the renter's own act. Scoping the check to the calling org would let a second landlord rewrite the name on a document a first landlord holds. |
| 2026-09-27 | **Supersedes the row above (client decision).** A landlord may correct the name of a renter who has signed **with this org**, with a required reason; the `name_corrected` SMS is then mandatory. A signature with **another** org still refuses (409 `renter_signed_elsewhere`). | The client needs to fix names on live tenancies. The snapshot rule keeps every signed document intact, so the rename only moves the live `parties` header; the reason plus the unconditional SMS make a bad edit visible. The cross-org refusal keeps the original concern: one landlord must not rewrite the name another landlord holds on a signed document. |
| 2026-09-20 | A rename never touches the contract snapshot: the frozen terms and the hash are byte-identical afterwards, and only the live `parties.*.name` follows the account. A test pins the document bytes and both hashes. | SPEC §5.5: the document is evidence. If a rename could rewrite it, the hash would stop meaning "this is what was signed". |
| 2026-09-20 | `PATCH /org/members/{id}` counts owners **after** the write, inside the transaction, and rolls back on zero; changing one's own role is refused outright (409 `cannot_change_own_role`) rather than allowed when harmless. | Counting first is a check-then-act two concurrent demotions can both pass. Refusing self-demotion outright means no single request can leave an org ungoverned, whatever the ordering. |
